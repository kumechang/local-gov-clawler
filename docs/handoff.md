# 自治体Webサイト構造解析クローラー 引き継ぎドキュメント

このドキュメントは、Claudeとの設計相談の内容を Claude Code に引き継ぐためのものです。
実装に入る前に、まず「0. 最初にやること」と「11. 未決事項」を確認してください。

---

## 0. 最初にやること(Claude Codeへ)

1. リポジトリ内の既存資産を確認する。ユーザーは**全国約1,900自治体の公式URL一覧**と、**サイトマップXMLを公開している自治体のサイトマップURL一覧**を作成済み。ファイルの場所・形式(CSV/JSONなど)・列構成は本ドキュメントでは把握していないので、実物を読んで把握すること。
2. 「11. 未決事項」のうち、実装前にユーザーへ確認すべきもの(言語、DB置き場所、リポジトリの公開/非公開など)を質問する。
3. 「9. パイロット計画」に沿って、**1県(20〜50自治体)の最小実装**から始める。全国展開はパイロットの結果を見てから。
4. 全国分をいきなり回さないこと。

## 1. 背景と目的

### 最終的に取りたい情報
- 全国の自治体サイトにしか載っていない**一次情報**。具体例として「公共グラウンドのうち、グラウンドゴルフが利用できる施設」を全国から集めたい。
- イベント情報(大会など)は、協会・公民館・広報PDFなど自治体サイト以外に載ることが多く、日付で価値が消えるため**今回の対象外**。更新頻度が低い公共施設情報を対象にする。

### 今回のスコープ(重要)
最初の目標は、グラウンドゴルフの施設抽出ではなく、**「全自治体Webサイトの浅い構造解析」**。

- 構造情報は、今後の別ジャンル調査(ピックルボールのコート、ごみ分別、子育て支援など)にも使い回せる**内部開発資産**として位置づける。売る・公開することは想定していない。
- 壊れたら作り直せばよい前提。複雑なメンテナンス機構は不要。
- グラウンドゴルフ(正確には「スポーツ施設・公共グラウンド」ジャンル)は、**構造解析がうまくいったかを測る物差し(受け入れテストの題材)**として使う。

### 想定している活用の流れ
```
構造解析(本タスク) → ジャンル別の入口(ハブ)ページ発見 → 該当ページ取得 → キーワードフィルタ → LLM構造化抽出
```
本タスクのスコープは、このうち**最初の「構造解析」と「ハブページ候補への到達」まで**。抽出工程は後続フェーズ。

## 2. 確定した方針(議論の結論)

| 項目 | 方針 |
|---|---|
| 解析の深さ | **浅く**。トップページ、robots.txt、サイトマップ、トップから2階層程度まで。全ページ巡回はしない |
| ジャンル | 検証用に**「スポーツ施設・公共グラウンド」**を1つ決める。グラウンドゴルフはその先の抽出工程で判断 |
| 取得方法 | **通常のHTTP取得を基本**。ヘッドレスブラウザ(Playwright等)は、本文が空・JS描画のページのみフォールバック |
| 予約システム | **対象外**(ユーザー判断)。ログインやセッションが必要なページには入らない |
| 解析の分担 | ルールで判定できるものはプログラム、迷うものだけAI(「6. プログラムとAIの切り分け」) |
| 実行環境 | **GitHub Actions**で実行 |
| IP対策 | まず直接取得の失敗率を測定し、必要なら国内プロキシ or self-hosted runner(「8. IP問題」) |
| 保存 | 生データ層と構造化層の2層。HTML原本は外部ストレージ寄り |

---

## 3. 非目標(やらないこと)

- 全ページのクロール、全文検索インデックスの構築
- 施設予約システムの中身の取得
- CAPTCHAやWAFの突破、robots.txtでDisallowされたパスの取得
- 複数IPへの分散によるレート制限の実質的な回避
- ページ内部のDOM構造(どのタグに何があるか)の保存。抽出はLLMに本文を渡して行うため不要
- 他社公開用のデータ提供、ページ本文の転載

## 4. 構造解析で取る項目(浅い解析)

### 自治体ごとに取得する
1. **基本情報**: HTTPステータス、リダイレクト後の最終URL、取得可否、取得所要時間
2. **robots.txt**: 内容の保存、Crawl-delay、Disallowの有無
3. **サイトマップ**: 有無、URL、ページ数、lastmodの有無と分布、トップレベルのパスごとのページ数
4. **CMSの推定**: generatorタグ、特定のCSSクラス名、フッター表記、URLの形式などによるルールベース判定。主要ベンダーは数種類に集中している想定なので、シグネチャを登録して判定する
5. **JS描画の要否**: HTTP取得した本文テキストが極端に少ない、`<noscript>`中心、などを検出
6. **トップページのナビゲーション**: 「分野別」「ライフシーン別」「組織別」などのメニューのリンク文言とURL。**これが最重要**。ジャンル別の入口発見に再利用する
7. **トップページのHTML原本**: 後から解析ロジックを改良しても再取得せずに済むように保存
8. **ハブページ候補**(スポーツ施設・公園・体育施設など): スコアリング結果とともに保存(「6」参照)

### 注意
- URLが `/soshiki/123/4567.html` のような数字IDのCMSも多く、URLだけでは中身を判別できない。その場合、サイトマップは「更新検知用」と割り切り、ナビゲーションのリンク文言を頼りにする。
- トップから2階層程度で止める。それ以上は必要になったジャンルのときに掘る。

## 5. データモデル(案)

ジャンルに依存しない作りにする。**ジャンル専用のカラムを自治体テーブルに足さない**(「自治体 × ジャンル → 入口URL」は別テーブル)。以下は叩き台なので、実装時に調整してよい。

### 5.1 `municipalities`(自治体)
- 自治体コード(全国地方公共団体コード等、既存一覧にあればそれを使う)、名称、都道府県
- 公式URL
- 状態(ステータス): `pending` / `fetched` / `failed` / `needs_review` / `done` など
- 最終取得日時

### 5.2 `site_profiles`(サイトプロファイル。自治体1件につき1レコード)
- サイトマップの有無とURL
- CMS種別(推定値)
- JS描画の要否 / 取得方法(`http` / `headless_fallback`)
- クロール設定(robots.txtのCrawl-delay、個別レート制限)
- プロキシが必要だったか(直接で成功したか)
- 各判定の**出所**: `auto`(自動判定) / `ai`(AI判定) / `manual`(手動確認済み)
- 最終検証日時

### 5.3 `genre_entrypoints`(自治体 × ジャンル → 入口URL)
- 自治体ID、ジャンル名(例: `sports_facility`)、入口URL
- スコア、判定の出所(`auto` / `ai` / `manual`)
- 検証日時、リンク切れフラグ

### 5.4 `nav_links`(トップページのナビゲーションのリンク)
- 自治体ID、リンク文言、URL、取得階層、取得日時
- 任意: 「どのページからのリンクか」(ハブ検出精度の後検証用。最初は省略可)

### 5.5 `pages`(取得したページの生データ層)
- URL、自治体ID、取得日時、HTTPステータス、ETag/Last-Modified、コンテンツハッシュ
- 本文テキスト(PDFはテキスト化したもの)
- HTML原本の保存先(外部ストレージのキー)

### 5.6 `extractions`(構造化層。後続フェーズ)
- 施設名、住所、利用区分(`専用` / `兼用` / `記載なし`)、料金、予約方法
- 根拠URL、根拠テキスト、抽出日時、抽出に使ったモデル・プロンプトのバージョン

### 保存場所
- 小さいうちは**SQLiteで十分**。後でPostgreSQL等へ移行できる設計にしておく。
- HTML原本は肥大化するので、**Cloudflare R2やS3などの外部ストレージ**に置くことを推奨。GitHub Actionsのartifactsは一時置き場と考える。
- リポジトリへのコミットでDBを保持する案もあるが、原本を溜めるとすぐ肥大化するので原本は入れない。

## 6. プログラムとAIの切り分け

原則: **ルールで白黒つくものはプログラム、文章の意味や言い回しの揺れを読む必要があるものだけAI。** AIは遅く、費用がかかり、結果もぶれるので、できるだけ後ろの工程に寄せる。

### プログラムで担う
- サイトマップの取得・パース、robots.txt確認、レート制限、リトライ、HTTP取得
- 差分検知(ハッシュ、ETag、lastmod)
- HTML本文抽出、PDFテキスト抽出
- CMS判定(シグネチャ照合)
- URLパターンによる絞り込み
- キーワードフィルタ(NFKC正規化したうえで、「グラウンドゴルフ」「グラウンド・ゴルフ」「グランドゴルフ」などの表記ゆれを正規表現で拾う。後続フェーズ)
- ジオコーディング(後続フェーズ)
- 保存、重複排除、ステータス管理

### ハブページ検出(最初はプログラム、迷ったらAI)
- リンク文言に「スポーツ施設」「体育施設」「公園」「グラウンド」などが含まれるかを点数化する。
- そのページから先に、施設名らしきリンクが並んでいるかも特徴量にする。
- **候補が1つに絞れたらそのまま採用。** 複数ある、または0件のときだけAIに回す。
- AIには**リンク文言とURLの一覧だけ**を渡して選ばせる(本文は渡さない。コストが小さい)。

### AIが必要なもの(後続フェーズ含む)
- 利用可否の判断(「グラウンドゴルフは利用不可」「大会時のみ」など、否定・条件の読み取り)
- 自由文からの構造化抽出
- PDFの表の解釈(〇印が付いた列が利用可能な種目、など)
- 施設名の名寄せ(住所が一致しない場合)

### AI出力はプログラムで検証する
- AIが示した根拠テキストが**原文に実際に含まれているか**を文字列照合する(作り話を機械的に弾く)
- 出力がJSONスキーマに合っているか確認する
- 住所がジオコーディングできるか確認する

### 判定の出所を必ず記録する
`auto` / `ai` / `manual` を区別して保存する。パイロットで「プログラムだけで確定できた割合」「AIに回った件数」を測り、全国展開時のコスト見積もりに使う。

## 7. 取得ルール(礼儀)

- **robots.txt**を確認し、Disallowのパスは取得しない。
- **1サイトあたり1リクエスト/秒以下**。IPが変わっても(プロキシ使用時も)守る。
- User-Agentに**連絡先を入れる**。
- 並列化は**自治体単位**で行う。同じ自治体に複数ジョブが同時に当たらないようにする。
- CAPTCHA・bot対策で明らかに弾かれたサイトは突破せず、`failed`(理由付き)として記録し、手動確認かスキップにする。
- 自治体サーバーは小規模なことが多く、過去にクロール負荷が問題になった事例もあるため、特に配慮する。
- 利用規約でクロールが禁止されているサイトは取得対象にしない。

## 8. 実行環境(GitHub Actions)とIP問題

### GitHub Actionsの設計
- **シャード分割(matrix)**: 自治体を50〜100件ずつに分けて並列実行。1ジョブ最大6時間、同時実行数にも上限があるため、これで1,900件でも収まる想定。
- **状態の保存**: runnerは毎回まっさらな環境。SQLiteへ複数ジョブが同時に書くと壊れるため、**各シャードは結果をJSON/NDJSONで出力し、最後のジョブで1つにマージしてDBへ反映する**。
- **ステータス管理**: 約1,900件を回すと必ず失敗するサイトが出る。途中で止まっても再開でき、失敗した自治体だけ再実行できる作りにする。
- **定期実行(再検証)**: 月1回程度を想定。scheduleトリガーは、公開リポジトリだと一定期間動きがないと自動停止されることがあるので、停止していないか時々確認する。
- **費用**: 公開リポジトリは無料枠が広く、非公開は月あたりの無料分に上限がある。条件は変わりやすいので、**最新の料金を確認**すること。
- **シークレット**: プロキシの認証情報などはGitHub Secretsに入れ、ログやartifactsに出力しない。

### IP問題(最大のリスク)
GitHub-hosted runnerは主に海外(米国)のクラウドIPから出る。自治体サイトの中には、海外IPやクラウドIP帯を拒否するところがあり、**手元PCより取得失敗率が高くなる可能性がある**。やってみないと分からない。

**対策の優先順位:**
1. **まず測る**: パイロット県で、次の3通りを比較する。
   - (a) GitHub Actionsから直接
   - (b) 国内プロキシ経由(ユーザーが用意予定)
   - (c) 手元のMacから(ベースライン)
2. 差がなければ、プロキシは不要。
3. 差が大きければ、国内プロキシ、またはMacを**self-hosted runner**にする(国内の家庭IPで出られる)。ただし**公開リポジトリでself-hostedを使うのはセキュリティ上のリスク**があるので、非公開リポジトリで使うこと。

**プロキシ利用の方針(ユーザーが用意する予定):**
- 用途は「海外IPだから弾かれていた自治体を、国内IPで正当に取れるようにする」こと。**拒否してくる自治体を迂回して取る用途には使わない。**
- プロキシ経由は**取得部分だけ**。自治体ごとに「直接で成功したか / プロキシが必要だったか」を `site_profiles` に記録し、必要なサイトだけプロキシを使う(従量課金のコスト抑制)。
- 国内データセンター系は安いが、クラウド帯をまとめて弾くWAFには効かないことがある。ISP系・住宅系は弾かれにくいが高い。
- 無料の公開プロキシは品質・安全性が低いので使わない。
- **失敗原因の切り分けを記録する**(タイムアウト / 403 / 接続拒否 / JS描画で本文が空 / 取れたが判断できない)。HTTPステータスやエラー内容から、IP制限・bot対策・サイト不安定をおおむね切り分けられる。「取得できなかった」と「取れたが判断できなかった」は区別し、**AIに回すのは後者だけ**。

## 9. パイロット計画

### 目的
全国展開前に、次の3点を数字で把握する。
- ハブページへの到達率(受け入れテスト)
- 取得失敗率(Actions直接 / プロキシ / ローカルの比較)
- AIに回る割合(=全国展開時のAIコストの見積もり根拠)

### 手順
1. 1県(20〜50自治体)を選ぶ。
2. **目視の正解データを10件程度**作る(それぞれの自治体で、スポーツ施設のハブページがどこかを手作業で確認)。到達率測定の基準になる。
3. トップページ取得 → robots.txt → サイトマップ解析 → CMS判定 → ナビゲーション抽出 → ハブ候補スコアリングまでを実装して回す。
4. 取得は3通り(Actions直接 / プロキシ / ローカル)で比較する。
5. 到達できなかった自治体の理由を分類する(リンク文言が特殊、JS描画、取得失敗など)。理由の多いものから解析ロジックを直す。
6. 結果をユーザーに報告し、全国展開に進むか判断してもらう。

### 受け入れテスト(暫定)
- 「構造データだけで、スポーツ施設のハブページ候補に**8割程度の自治体で到達できる**」こと。
- この数値は暫定。パイロットの結果を見てユーザーと調整する。

### 計測しておく指標
- ステータス別の自治体数(成功 / ハブ候補複数 / ハブ未検出 / 取得失敗)
- プログラムだけで確定できた割合、AIに回った件数
- 1自治体あたりのリクエスト数・所要時間
- ヘッドレスのフォールバックが必要だった割合
- Actions直接 vs プロキシ vs ローカルの失敗率

## 10. 実装の方針メモ

- **言語は未決定**(Python / TypeScript のどちらでも同等の構成が組める)。ユーザーと相談して決める。参考までに、Pythonなら取得は `httpx`、本文抽出は `trafilatura` / BeautifulSoup、PDFは `PyMuPDF` / `pdfplumber`、フォールバックは Playwright。
- **抽出スキーマ・プロンプトは設定として外出し**にし、ジャンルを差し替えてもコード変更が要らないようにする。ただし、最初から汎用化しすぎない。**「ジャンルだけ差し替え可能」程度**にとどめる。
- **パイプラインそのもの**(取得、レート制限、サイトプロファイル管理、キーワードフィルタ、LLM抽出)が最も再利用価値が高い。部品として分離しやすく書く。
- サイトプロファイルは古くなる(数年おきのリニューアルでURLが総入れ替えになる)。保存したハブページが404になったら、プロファイルを破棄して発見からやり直す程度の軽い仕組みで十分。
- 取得とAI解析は**別ジョブ**に分ける。Actionsのクローラーがステータスを出力し、AI解析は要確認の自治体だけを対象にする。

## 12. 後続フェーズ(参考。今回のスコープ外)

構造解析が受け入れテストを通過したあとの流れ。

1. ハブページの配下から、施設ページ(HTML/PDF)を取得して `pages` に保存
2. 表記ゆれを含むキーワードで機械的にフィルタ
3. ヒットしたものだけをLLMに渡し、施設名・住所・利用区分(専用/兼用/記載なし)・料金・予約方法を抽出
4. 根拠テキストの原文照合で検証
5. 住所をジオコーディングして地図化

**見逃しの注意**: 多目的広場でグラウンドゴルフができても、ページに種目が明記されていなければ拾えない。見逃しゼロにはならない前提にする。補完候補として、各都道府県・市区町村のグラウンド・ゴルフ協会サイトの「活動場所」一覧、自治体の公共施設オープンデータ、国土数値情報(位置の土台として)がある。

**公開時の注意**: 公開するのは事実情報(施設名・住所・利用可否)と出典リンクにとどめ、ページ本文をそのまま転載しない。根拠URLと該当テキストは必ず一緒に保存しておく。
