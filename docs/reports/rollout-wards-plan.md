# 政令市の区(171件)の扱いの計画と事前基準(結果を見る前に記録)

関連: D-063(段階1では解析しない)、D-096、D-097 / 前提: `docs/reports/national-v11-overview.md`

## 事実(マスタとv11の結果)
- 区は20の政令市に171件。**171件すべてが親市と同じホスト**(パスだけ違う。例: 札幌市中央区 `…/chuo/index.html`)。サイト、robots.txt、サイトマップ、CMSは親市と共通
- 親市のハブ(v11): 20市のうち15市が確定(札幌・仙台・さいたま・千葉・川崎・相模原・新潟・静岡・名古屋・京都・岡山・広島・北九州・福岡・熊本)。確定できなかったのは横浜(同点)・大阪(未確定)・堺(同点)・神戸(未確定)の4市。浜松市は『公園』を確定(疑わしい)
- 親市のスポーツ施設の一覧は、通常、市内全域(各区の施設を含む)を載せている。区ごとのサイトには、区のスポーツセンター等の案内がある場合がある

## 方針(D-096)
1. **区も個別に解析する**(区のトップから、v11のロジックでハブを探す)。route=`actions_direct_v11_wards_<ローマ字>`(15府県)、`scope=designated_city_ward`、軽量形式
2. **区の有効なハブ(`effective_hub_url`)= 区に固有のハブが見つかればそれ、無ければ親市のハブを引き継ぐ**。区と親市の関係を `own`(区固有・親と異なる)/ `same`(親と同じ)/ `ward_only`(区だけ確定)/ `inherit`(区は未確定、親が確定)/ `none`(どちらも未確定=手動確認)に分類し、`data/summary/wards.csv` と `wards.md` に出す(`localgov-crawler ward-report`)
3. **同じホストへのリクエストは、1ホスト1リクエスト/秒を守る**: 区は親市と同じホストなので、今までの『自治体ごとに別のワーカー』では、同じホストに複数のワーカーが同時にアクセスしてしまう。ホスト単位で1つのワーカーが順番に処理し、Fetcher(最小間隔の管理)を共有するよう修正した(`cli.group_by_host`)。通常の自治体は、ホストが別なので挙動は変わらない

## 事前基準
| # | 項目 | 基準 | 満たさないとき |
|---|---|---|---|
| 1 | 取得失敗率(`fetch_failed`+`robots_blocked`) | 全体で10%以下。親市のホストが取得できている(親市の結果が確定または未確定=取得できた)ので、区の失敗は主にパスの問題 | 失敗の理由別に分析。403/429の集中はWAFの疑い |
| 2 | ブロック兆候 | 403・429が出た区が全体の5%未満 | 同上 |
| 3 | 親市の確定との整合 | 親市のハブが確定している15市の区(約130件)のうち、区の確定が親市のハブと『同じ』または『区に固有』で、題名が明らかに一覧でないもの(予約・使用料・整備事業など)が10%以下 | 区の確定のルールを見直す(区は親市の引き継ぎだけにする) |
| 4 | 平均リクエスト数 / 平均容量 | 15以下 / 35KB以下 | 見直し |

報告のみ: 関係(own/same/ward_only/inherit/none)の件数、`effective_hub_url` が分かる区の数、手動確認が必要な区の数(none)、政令市別の内訳。

## 次
基準を満たせば、区の扱いは『区に固有のハブがあればそれ、無ければ親市のハブ』で確定とする。noneの区は、親市が確定していない4市(横浜・大阪・堺・神戸)に集中する見込みで、親市の手動確認で解決できる。
